- [x] Fixed and verified locally. See [repair, before/after evidence and limitations](UI06-repair.md) and [acceptance](ui06-acceptance.json). The original review below is retained as failure evidence.

Bodies / Body Type changes five actual body IDs to kinematic. On real CPU and ordinary/native standalone GPU, Kinematic transparency is checked, actual type getters return1 for all five bodies, but the real RenderFrame submits0 transparent instances instead of5. Original IDs and origins survive each type setter. Screenshot and getter evidence are in [the acceptance receipt](body-view-controls-acceptance.json) and [CPU-first grid](body-view-controls-grid.jpg).

`box3d/samples/gfx/debug_adapter.c:457` populates DebugShape.bodyType from a getter at shape creation. DrawShape lines861–869 uses this stored value for transparency; it does not refresh the type when the physics body changes. Only Bodies / Body Type actively calls SetType in the registered sample sources (ragdoll occurrences are commented). The adapter implementation is shared, so future runtime type changes are also applicable. Material defaults also use that metadata; their runtime visual effect is not yet independently measured.

Both combined routes additionally submit0 Dynamic transparent instances in the first CPU pane, compared with7 on standalone CPU/GPU. The before image shows opaque CPU bodies and transparent GPU bodies. The diagnostic metadata row is emitted on the first RenderFrame and therefore quantifies the CPU pane only. Combined callbacks use CPU shape IDs while public b3Shape_GetBody/GetType route to GPU; this is a provenance hypothesis requiring the smallest getter trace before repair. Do not claim second-pane numeric counts from first-pane stats.

The original review included no repair. The subsequent native adapter/getter repair leaves Box3D/WASM unchanged; no trajectory matching is claimed.
