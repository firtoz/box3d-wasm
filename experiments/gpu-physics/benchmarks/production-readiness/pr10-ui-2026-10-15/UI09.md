# UI09 — GPU Replay UI misreports unsupported loading as a bad file

- [x] Fixed and verified locally; [repair and CPU-first before/after evidence](UI09-repair.md).

The actual CPU saves and successfully loads a valid recording, with forward/back and endpoint/home/play/pause working. All four GPU routes offer Replay / Open and the Load modal. Loading the same verified bytes yields `failed to open file`, with no unsupported/unavailable explanation inside that modal. The native recording/player APIs are explicitly excluded from the release scope; their stderr says not implemented, but the user-facing modal suggests a bad file.

[Acceptance and actual modal text](recording-replay-acceptance.json) preserve the valid producer hash and each route's failed UI-message check. The assertion deliberately excludes unrelated `Recording unavailable with GPU physics` text in the sidebar. `ReplayViewer::CreatePlayer` maps the null recording return to the generic file-open message. Later repair should state the native-player exclusion in the appropriate UI and keep real CPU recording/replay functional; implementing a native player is outside PR10.

The generated native GPU/combined UI now explains the exclusion, offers Close, hides ineffective load controls, and guards unavailable API calls. Actual CPU valid/missing-file paths still work. Final46-character status fits the native64-byte screen buffer; playback remains unsupported.
